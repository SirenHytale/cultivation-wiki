# Cultivation Wiki — Next.js

The xianxia.dev wiki, rebuilt on Next.js 16 (App Router, React 19) with real
server-side rendering.

The previous site — plain static HTML generated by the Python tools in
`../tools/` — is still present at the repo root and is still what GitHub Pages
serves. Nothing here is live until the DNS cutover below. Both can coexist
indefinitely.

## Running it

```bash
npm install
npm run dev      # http://localhost:3000
npm run build    # production build
npm start        # serve the production build
```

Node 20.9+ is required (Next 16). This project was built against Node 24.18.1.

## Why the URLs look the way they do

Every URL is unchanged from the static site: English pages serve at the root
(`/dao/`) and Chinese mirrors them under `/zh/` (`/zh/dao/`). No `/en` prefix
was introduced, so existing links, bookmarks and search results still resolve.

That is why there are **two root layouts** rather than one `[lang]` segment:

```
app/(en)/layout.tsx      <html lang="en">      → /, /dao/, /planner/
app/(zh)/layout.tsx      <html lang="zh-CN">   → /zh/, /zh/dao/, /zh/planner/
```

A single root layout could not vary `<html lang>` per language without opting
every page out of static generation. Next resolves the static `zh` segment
ahead of the English `[slug]`, so the two trees do not collide.

## Content

Pages are MDX under `content/en/` and `content/zh/`, one file per slug
(`index.mdx` is the home page). They were converted from the generated HTML by
`../tools/html_to_mdx.py`.

Frontmatter:

| Key | Meaning |
| --- | --- |
| `title` | Page title; also the `<title>` and breadcrumb |
| `description` | Meta description and social card text |
| `group` | English sidebar group name — drives the eyebrow and its glyph |
| `toc` | Heading levels for the rail; defaults to `h2,h3` |
| `mermaid` | Set when the page carries a diagram |

Theme components come from `components/mdx/` and are used directly in the MDX:
`<Note>`, `<Card>`, `<CardGrid>`, `<Panel>`, `<Divider />`, `<Chip>`, `<Tag>`.
These replace `../tools/enhance.py`, which matched prose substrings with regex
and silently dropped a page's styling whenever upstream wording changed.

Pinned heading anchors are written `## Heading \{#anchor\}`. **The braces must
stay escaped** — MDX lexes a bare `{` as a JSX expression and fails the parse
before any plugin runs. `remarkHeadingIds` in `components/DocPage.tsx` strips
the marker and pins the id, which is how the English and Chinese pages share
one anchor.

## Adding or changing a page

1. Edit or add `content/<lang>/<slug>.mdx`.
2. Add a `data/nav.js`-equivalent entry in `lib/nav.ts` (with `zhPage: true`
   once a Chinese version exists), or the page renders but is unreachable.
3. If you touched a diagram, re-run the prerender (below).

Nothing else needs regenerating — the search index, sitemap, breadcrumbs and
prev/next all derive from the MDX and `lib/nav.ts` at build time.

## Diagrams

`node ../tools/prerender_mermaid.mjs` renders every ```mermaid fence to SVG in
both themes and writes `lib/data/diagrams.json`. CSS shows one variant and
hides the other, so switching Yin/Yang is instant and no diagram renderer ever
reaches the browser.

It needs a local browser (headless Edge), so it is **not** part of `next build`
— Vercel builds stay browser-free. Run it locally and commit the JSON. A
diagram with no prerendered entry falls back to the client renderer, so a stale
run degrades rather than breaks.

## The interactive tools

`/planner/` and `/calculator/` keep their original logic verbatim
(`lib/tools/`), rewrapped from IIFEs into ES modules by
`../tools/port_tools.py`. The planner's data is generated from the mod's own
`SkillTreeRegistry`; the calculator hardcodes the real Qi curve. Both were
verified to produce numerically identical output to the static site.

Their markup is injected from `lib/tools/shells.ts` rather than written as JSX
— the `id` and `data-*` attributes are a contract with that logic, and
hand-transcribing ~15 KB of form inputs would risk a silent typo. It is still a
build-time constant rendered on the server.

## Things that must not break

- **`/api/get/**.json` is a live endpoint.** Deployed Cultivation, JadeSlip and
  SoulRings clients poll it for update and compat checks. The files live in
  `public/api/get/` and get explicit cache headers in `next.config.ts`. Do not
  put a route handler under `/api` — that prefix belongs to these.
- The site's own search endpoint is therefore at **`/wiki-search/`**, not
  `/api/search`. Fetch it *with* the trailing slash; `trailingSlash: true`
  means the bare path 308-redirects.
- `styles/xianxia.css` is a copy of the static site's stylesheet and is kept
  byte-identical so the two do not drift. Framework-specific changes belong in
  `styles/next-overrides.css`.

## Deploying to Vercel

1. Import `SirenHytale/xianxia.dev` as a Vercel project.
2. Set **Root Directory** to `web`. Everything else is detected.
3. Deploy and verify on the `*.vercel.app` URL — particularly
   `/api/get/version/cultivation.json`, since mods depend on it.
4. Add `xianxia.dev` as a domain in Vercel, then repoint DNS away from GitHub
   Pages. Until DNS moves, GitHub Pages keeps serving the old static site, so
   the cutover is reversible.
5. After the cutover, the root-level page directories and `../tools/` Python
   generators are dead weight and can be deleted — but keep `html_to_mdx.py`
   and `port_tools.py` if you want the migration to stay reproducible.

`CNAME` and `.nojekyll` at the repo root only matter to GitHub Pages. Leave
them until the cutover is confirmed.
